# Four artifact workflow

## Responsibility and gates

Use A 扫描报告 -> B 设计原子 Token 规范 -> C 治理审计 -> D 治理报告. These are artifacts, not four executable web steps. Codex selects scope, scans, diagnoses, applies approved changes, verifies and updates artifacts. HTML renders evidence, edits proposals and exports decisions; it does not launch Codex or GitHub operations.

A links module -> functional area -> subfunction -> UI element -> state/property -> source/opening path. Observed duplicate/unused candidates and broken references are problem clues, not deletion authority. Keep complete inventory separate from the smaller issue list. Evidence and inferred opening paths must not masquerade as runtime checks.

B defines the shared atomic standard only. Edit category, name, meaning, intended scope, underlying typed style owner and theme/state values together. Label generated defaults as proposals, not scanned values. Confirm the entire current framework once and pin its category versions and framework/binding revisions. User changes to a locked definition create a new revision; preserve the earlier snapshot. Do not put old-to-new occurrence decisions or an audit-scheme tab inside B.

C is generated by Codex from consumer evidence against confirmed B. A partial batch may use a subset of the confirmed framework while unrelated categories remain outside that batch. Adoption of a suggestion records a decision, not execution permission or completion. Before source writes obtain batch approval tied to action IDs, framework/binding revision, source baseline, affected scope and required checks. A framework edit triggers impact analysis and invalidates affected proposals/approvals; unaffected decisions survive only with evidence. Never silently retarget old approvals.

Update C after every round, keeping decision, authorization, source application and verification/acceptance distinct. Use the receipt statuses and counting rules in module-governance.md. D aggregates distinct actions at agreed-scope closure, not a single batch or approved-item count. Partial delivery and unverified states stay explicit. Include actual changes, comparable before/after units, visual evidence and residuals; never manufacture a complete report before execution.

## C: attention-first interaction

- Navigate by business module, then subfunction/UI element. Initially show counts and only groups needing attention: ambiguous decisions, blockers, failed checks and acceptance requests.
- Collapse repeated occurrences into one question only when semantic role, property/layer, mode/state, target, action and evidence qualification are compatible. Equal values alone do not qualify. Preserve all occurrence IDs and allow an exception to split out of a group.
- Default to collapsed groups. On expansion prioritize the element/specimen, current versus target, one concise reason and editable action/target. Put locations, opening paths and source evidence behind details. Distinguish DOM specimens from actual page screenshots.
- Permit users to change suggestions, including migrate/merge/delete, scoped retention or defer. Deletion still requires qualification; an invalid choice records a blocker, never authorizes unsafe removal. Retention/defer are decision dispositions, not extra final lifecycle actions.
- Hide resolved details by default but retain searchable audit history and reversible unexecuted decisions. Reversing an executed decision requires a new authorized change, not a UI-only undo.
- Do not ask the user to approve every routine occurrence. Summarize qualified routine actions for batch authorization. Keep completed/unchanged/excluded items accessible without presenting them as pending questions.

## Fixed templates and handoff

Implementation and renderer contracts: [fixed-html.md](fixed-html.md). The primary entrypoints are now shipped; legacy diagnostics remain supporting evidence and must not be presented as completed B/C/D.

Reuse maintained offline HTML templates; populate versioned data rather than redesigning each run. Four navigation entries identify artifacts, not app administration or execution buttons. Show only real local operations: edit, confirm, filter, inspect, export/import. An absent PR may offer a copyable request for Codex, not a fake create-PR action. Link a real PR only after verified creation.

Exports identify project, scan/source baseline, schema, framework and binding revisions, stable IDs and decisions. Validate import compatibility; source facts remain immutable. Browser autosave is a draft cache, not the durable record. Explicit chat confirmation/export handoff is required; no automatic browser-to-agent bridge is assumed. Keep demo data separate and non-executable.

The manual, B, runtime CSS/TS and permanent source map share approved definitions; desired and observed values remain distinct until verified. C supplies action history; D supplies evidence-backed outcome. Include DESIGN-SYSTEM.md, actual style owners, semantic-to-source map, migration/execution contract and residual records in D's delivery index. Final MD must not present an unimplemented target as current production truth.

## Compatibility and acceptance

Legacy `design-review.html` combines framework and audit; it is not compliant merely because its title changes. `visual-regression.html` is supporting D evidence. Keep existing command/schema names until real implementation changes are tested; do not invent a new command or relabel incompatible payloads. The documented review-v2/implement-v1 mismatch remains an execution blocker.

Check the four views have distinct responsibilities, shared stable IDs/version links and honest lifecycle states. Exercise: edit B -> impacted C proposal becomes stale -> no old approval execution; adopt in C -> no source change implied; apply without visual access -> awaiting acceptance, not verified; finish one batch -> C receipt, not project-complete D. Validate template rendering/interactions when templates change. Documentation-only updates do not establish that generators implement these behaviors.
